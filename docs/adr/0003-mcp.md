# ADR 0003 — MCP as the reusable AI-facing capability boundary

**Status:** accepted · **Date:** 2026-09-06

## Context

Three consumers need the same travel capabilities: the WhereNext agent, the
RouteCheck agent, and the admin verification assistant. They need *different
subsets* with *different permissions*. Without a boundary, each would grow its
own copy of "search evidence" and "get transport", and the permission
differences would live in whichever function happened to be called.

## Decision

`packages/travel_mcp` is a real MCP server — typed input/output schemas,
protocol-level argument validation, JSON-RPC. It exposes 14 tools across
evidence, place, transport, booking, verification and trip-state.

Two transports, one code path:

- **in-process** — agents connect over in-memory streams via a real
  `ClientSession`. Validation and error shaping are the protocol's, not a
  helpful wrapper's.
- **stdio** — `travel-intelligence-mcp` for external clients.

The gateway owns the *interface* and none of the implementation. Everything
behind a tool arrives through the `TravelBackend` protocol, which is why the
package has no database, provider or application imports.

Permissions are declared per consumer in `agents/common/tools.py`:

| Consumer | Tools | Write trip state |
| --- | --- | --- |
| WhereNext | 13 | yes |
| RouteCheck | 12 | no |
| Admin assistant | 7 | no |

## What deliberately does not go through MCP

Ordinary internal CRUD. Trip creation, analysis persistence and evidence lookup
by id are direct repository calls. Routing them through JSON-RPC would add
serialisation and a failure mode for no benefit. MCP carries reusable AI-facing
capabilities; that is the whole boundary.

## Alternatives considered

**Plain Python functions with an allowlist.** Simpler, and would satisfy the
permission requirement. Rejected because it gives no schema publication and no
external reuse — an outside client could not use these capabilities at all.

**HTTP microservice.** Same reuse, more operational surface, no typed tool
contract for a model consumer.

## Consequences

Good: one definition of every capability, published schemas, per-consumer least
privilege, external clients work unchanged, and tool-call failures are visible
at a protocol boundary rather than swallowed inside a helper.

Bad: an extra hop for in-process calls (in-memory streams, so cheap but not
free), and the `TravelBackend` protocol must be kept in sync with the tool list.
